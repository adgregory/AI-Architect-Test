# Spike 01 — OCR engine selection

**Status:** planned

## Question

Which OCR engine should extract text **and word positions** from scanned PDFs,
given accuracy, latency, hardware acceleration (ONNX / Apple GPU), resource
usage, and Docker footprint?

## Candidates

Docling is a document-conversion pipeline (layout + reading order) that
delegates OCR to a pluggable engine, so it is tested with its default engine.
PaddleOCR is tested both natively and through ONNX Runtime (RapidOCR runs the
same PaddleOCR models exported to ONNX), which is the with/without-ONNX
comparison.

| ID | Candidate | Runtime | ONNX | Accelerators on this machine |
|----|-----------|---------|------|------------------------------|
| `tesseract` | Tesseract 5 via `pytesseract` | Native C++ (LSTM) | Not possible — its model format is not ONNX | CPU only |
| `paddle` | PaddleOCR (native) | PaddlePaddle | No (native run) | CPU only — Paddle GPU builds require CUDA |
| `paddle-onnx` | PaddleOCR models via RapidOCR | ONNX Runtime | Yes | CPU EP, CoreML EP (Apple GPU/ANE) |
| `docling` | Docling, default OCR (EasyOCR) | PyTorch | No (layout + OCR are PyTorch) | CPU, MPS (Apple GPU) |

This gives **6 benchmark configurations**: `tesseract/cpu`, `paddle/cpu`,
`paddle-onnx/cpu`, `paddle-onnx/coreml`, `docling/cpu`, `docling/mps`.

**Hardware:** Apple M5 Max, macOS. No CUDA. Apple GPU results via MPS/CoreML
are part of the spike's findings, not a proxy for CUDA servers.

## Dataset

### Ground truth (exact, not model-generated)

`scripts/generate_test_pdfs.py` draws each page with Pillow at 150 DPI from
hard-coded text lines. Re-running its page generators reproduces the committed
`sample_pdfs/` images **exactly** (max pixel diff 0 after the same JPEG
encoding Pillow applies when writing the PDF — verified). So ground truth is
derived from the generator, not from an OCR/LLM reference:

- **Text:** the exact lines drawn on each page.
- **Word boxes:** computed with the same font metrics (`ImageDraw.textbbox`)
  at the drawn positions, in 150 DPI pixel space and in PDF points (72 DPI).
- **Names:** the expected-name lists in the generator, located to their word
  boxes.

### Pages

```
spikes/01-ocr/data/
├── ground_truth/                 # one JSON per page: text, word boxes, names
├── clean/                        # the 5 original pages (150 DPI PNG)
└── degraded/
    ├── noise/                    # Gaussian + salt-and-pepper noise
    ├── skew/                     # rotation ±0.5–3°
    ├── blur/                     # Gaussian blur
    ├── jpeg/                     # heavy JPEG compression
    ├── low_dpi/                  # downsampled to 100 and 72 DPI
    └── scan/                     # combined: skew + noise + blur + JPEG
```

Each degradation is applied at several severities with fixed seeds, yielding
roughly 150–200 pages. Geometric transforms (skew, resampling) are applied to
the ground-truth boxes with the same affine transform, so box ground truth
stays exact. `data/` is generated by a script and git-ignored; only the
generator is committed.

## Metrics

### 1. Accuracy — CER / WER
- Per-page **CER** and **WER** via `jiwer`, after light normalization
  (Unicode NFKC, collapsed whitespace). Reported per degradation profile.
- **Name recall:** fraction of expected names found verbatim in the OCR text
  (case-sensitive and case-insensitive). This is what breaks the `/extract`
  endpoint, and can diverge from global CER.

### 2. Latency — p90 / p95 / p99
- Input to every engine is the same page image, so PDF rasterization is
  excluded and identical across engines.
- **Cold start** (process start → model loaded → first page) reported
  separately.
- **Warm latency:** 3 warm-up pages discarded, then every page × 3 repetitions;
  report p50, p90, p95, p99, mean.

### 3. ONNX
- `paddle` vs `paddle-onnx/cpu` vs `paddle-onnx/coreml` isolates the ONNX
  effect on the same models (accuracy should match; latency/resources differ).
- Tesseract and Docling (default) are recorded as non-ONNX, with the reason.

### 4. Resources — CPU, GPU, memory, disk
- **CPU / memory:** a `psutil` sampler (50 ms) on the benchmark process and
  children: mean/peak CPU %, peak RSS.
- **GPU:** MPS allocated memory (`torch.mps`) for Docling; GPU active
  residency via `powermetrics` for all GPU runs. `powermetrics` needs `sudo`,
  so that step is a command the user runs; if skipped, GPU utilization is
  reported as unavailable.
- **Disk:** installed size of each engine's environment plus downloaded model
  files. A minimal CPU-only Docker image per engine (`python:3.12-slim` +
  engine) gives the real image size.

### 5. Positional output (bounding boxes)
For each engine, document what its API returns and score it against
ground-truth word boxes:
- **Granularity:** word / line / block; box shape (axis-aligned vs
  quadrilateral); coordinate space and origin.
- **Name localization:** for each expected name, the best predicted box
  (union of matching word boxes, or the containing line/block box); report
  IoU against the ground-truth name box and the share with IoU ≥ 0.5.
- **Word-level derivation:** where the engine is line-level, test its native
  word-box option if any, and note the extra work needed otherwise.

## Method and isolation

Each engine gets its **own uv environment** so their dependency trees
(PaddlePaddle, PyTorch, ONNX Runtime, NumPy 2) don't conflict with each other
or with the app's lockfile:

```
spikes/01-ocr/
├── README.md
├── dataset/          # ground-truth + degraded page generator
├── common/           # engine interface, metrics, resource sampler, report
├── engines/
│   ├── tesseract/    # pyproject.toml + uv.lock + adapter
│   ├── paddle/
│   ├── paddle-onnx/
│   └── docling/
├── run.py            # runs one configuration, writes results/<config>.json
├── report.py         # aggregates results into tables
└── results/          # committed JSON + summary tables
```

Each adapter returns the same structure (text + boxes in a common coordinate
space), so metrics are computed identically across engines.
